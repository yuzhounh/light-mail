## 2026-10-19：启动显示无账户

已确认本次根因是工具执行环境和真实桌面环境的 AppData 文件视图隔离。两边的 `%APPDATA%\my-mail` 路径字符串相同，但目录文件系统标识不同：工具进程能看到四个账户和缓存；用户从桌面打开的真实 v0.1.4 进程内，普通 `fs` 与 `original-fs` 都确认 `accounts.json` 不存在，账户接口和界面均为零。该桌面进程自己的诊断日志也记录零账户。不能把另一环境中的 `count:4` 当作这个桌面窗口已经恢复的证据。

之前仅在工具环境核对文件、从工具启动后检查恢复，未证明桌面启动的数据视图一致，因而误判为启动加载故障。保留失败进程并直接检查其文件存在性、目录标识、接口和界面状态，才确认了真实原因。

已将原账户、设置、草稿和缓存恢复至真实桌面进程实际使用的目录。账户凭据使用一次性加密移交，并由桌面进程重新加密保存，没有覆盖桌面环境的加密密钥，也没有把明文密码写入临时文件。保留当前桌面窗口位置，恢复原有设置和分栏偏好；258 个缓存文件逐一通过 SHA-256 校验。迁移临时文件及临时诊断端口已清理。

恢复验证来自同一个真实桌面数据视图：四个账户可解密、四个邮箱分组和邮件列表正常显示；从这个桌面进程自身正常退出并重启后，仍可解密四个账户并加载邮件。恢复验证时的版本为 v0.1.4，本次根因通过数据恢复解决；安装包不包含自动跨环境迁移功能。随后已从该真实桌面上下文完成 v0.1.5 更新，并再次确认账户、邮件和数据目录一致。

后续更新必须以真实桌面进程看到的数据、版本和界面为准，核对目录文件系统标识，不能只比较路径字符串或读取工具环境的账户文件。已运行的桌面客户端可从自身重启；从工具启动得到的成功结果不能替代桌面启动验证。不要清理任一原数据目录，也不要反复要求用户重新添加邮箱。

此前同时发现并通过故障注入修复的代码缺陷属于独立的健壮性改进，不能再记作此次数据视图隔离的根因：

- `Promise.all` 捆绑账户、设置和草稿；可选设置或草稿加载失败会阻止账户进入界面。
- 账户元数据通过解密全部凭据取得；单个凭据异常会阻断整个账户列表。
- 账户 JSON 读取错误被吞掉并返回空数组，无法区分读取失败和真正没有账户；后续保存还有覆盖已有文件的风险。
- 启动读取只执行一次，错误提示消失后不会自动恢复；初始化期间也显示“未添加账户”。

修复后，账户元数据独立加载，不依赖密码解密或 Windows 开机启动项查询。读取失败保留已有账户，显示持久错误状态，按 0.5 秒递增至 30 秒的间隔自动重试，也可手动重试。已有邮件缓存但账户文件缺失时报告异常，不按新用户处理。连接凭据逐账户读取，失败账户独立重试。

`%APPDATA%\my-mail\startup-diagnostics.jsonl` 记录阶段、时间、账户数量及错误码，不记录密码、账户地址或邮件内容；文件超过 64 KiB 时保留最近记录。后续应读取失败现场的日志，而不是先重启后推测原因。

## 新邮件后台缓存

旧监听器只获取信封和标记，在正文尚未缓存时发送通知。

新流程在只读 INBOX 连接上使用 BODY.PEEK 获取完整来源、解析正文，写入正文和列表缓存后才推进 UID 检查点、更新界面和发送通知。失败不跳过 UID，5 秒后自动重试。通知点击优先打开本地正文，不等待网络列表完成。预取不会将邮件标记为已读。

缓存保存正文、内嵌图片及附件元数据。独立附件文件仍按需保存；外部图片 URL 的远端加载不属于正文缓存。
